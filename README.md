# DevOps ASP.NET 9 Demo

Minimalistyczny projekt DevOps oparty o ASP.NET 9 Web API, Docker i GitHub Actions.

## 🎯 Cel projektu
Celem projektu jest zaprezentowanie pełnego procesu DevOps:
- tworzenie aplikacji webowej
- testy jednostkowe
- CI/CD (GitHub Actions)
- konteneryzacja (Docker)
- wdrożenie do Azure
- monitoring i bezpieczeństwo

## 🧰 Technologie
- .NET 9 (ASP.NET Web API)
- Docker
- GitHub Actions (CI/CD)
- Azure App Service (Containers)
- Azure Application Insights
- Infrastructure as Code (Bicep)

## 📡 Endpointy
- `GET /` – status aplikacji
- `GET /products` – dane z zewnętrznego API (CoinGecko)














## Plan projektu DevOps Poniższy plan przedstawia szczegółowe kroki realizacji projektu DevOps, od utworzenia repozytorium po prezentację aplikacji. Zadania są ułożone mniej więcej od najprostszych do najtrudniejszych, z uwzględnieniem zależności między nimi. Repozytorium i backlog projektu. Utwórz nowe repozytorium na GitHubie lub w Azure DevOps. Dodaj plik README z opisem projektu i instrukcją uruchomienia. Skonfiguruj backlog używając GitHub Projects lub Azure Boards i rozbij projekt na szczegółowe zadania (issues/work items) odpowiadające kolejnym etapom. Połącz commity i PR-y z zadaniami backlogu (np. używając składni AB#ID dla Azure Boards). Utwórz przynajmniej jedną gałąź roboczą (feature) i zgłoś Pull Request do głównego brancha, a następnie go zmerguj. Podstawowa aplikacja i testy. Zaimplementuj prostą aplikację ASP.NET Core w C#. Zdefiniuj dwa endpointy: GET / (np. zwraca komunikat powitalny) i GET /products (zwraca listę produktów w formacie JSON). Można opcjonalnie dodać prosty front (np. w Vue), ale ze względu na minimalizm lepiej skupić się na backendzie. Jeśli potrzebne, połącz się z zewnętrznym API (np. pobierając dane z CoinGecko) lub użyj lekkiej bazy (SQLite) do przechowywania danych. Utwórz projekt testowy (np. xUnit) i napisz co najmniej 2 testy jednostkowe – np. sprawdzające poprawność odpowiedzi endpointów lub logiki aplikacji. Pipeline CI (ciągła integracja). Skonfiguruj pipeline CI używając GitHub Actions lub Azure Pipelines. Dodaj kroki budowania projektu (dotnet build) i uruchamiania testów (dotnet test), a także publikacji wyników testów (np. raportu pokrycia). Pipeline powinien wyzwalać się przy każdym pushu lub Pull Requeście. W ramach CI można też uruchomić statyczną analizę kodu lub linting. Takie etapy CI/CD są typowe w Azure Pipelines – oficjalna dokumentacja pokazuje przykładowy workflow, gdzie w pipeline PR uruchamiany jest build i testy, a po scaleniu do main kolejny pipeline wykonuje kolejne testy i publikuje artefakty. Konteneryzacja aplikacji. Napisz Dockerfile (np. wieloetapowy) dla aplikacji, używając oficjalnego obrazu .NET jako bazy. Zbuduj obraz i przetestuj go lokalnie (docker build, docker run). Konteneryzacja zapewnia przenośność i spójne środowisko wykonawcze – jak podkreśla dokumentacja .NET, „kontenery mają wiele zalet: są niezmienne, zapewniają przenośną architekturę i umożliwiają skalowanie”. Dzięki temu ta sama aplikacja będzie działać identycznie na różnych środowiskach. Pipeline CD (ciągłe dostarczanie) i wdrożenie na Azure. Skonfiguruj pipeline CD, który po zbudowaniu aplikacji zajmie się jej wdrożeniem. Możesz użyć GitHub Actions (np. akcja Azure/webapps-deploy) lub Azure Pipelines. Kroki pipeline: zbuduj obraz kontenera i wypchnij go do Azure Container Registry (ACR), a następnie wdroż go na Azure Web App for Containers lub bezpośrednio na Azure App Service. Alternatywnie zrób dotnet publish i deploy do Azure App Service/Function. Po poprawnym wdrożeniu aplikacja będzie dostępna publicznie (np. pod adresem *.azurewebsites.net). Na tym etapie warto również skonfigurować zmienne środowiskowe i połączenia (np. do bazy danych czy API) w ustawieniach aplikacji w Azure. Kubernetes (AKS). Jeśli chcesz rozwinąć projekt o Kubernetes (choć jest to trudniejsze), utwórz klaster Azure Kubernetes Service (AKS). Przygotuj manifesty K8s (Deployment, Service, ewentualnie Ingress) dla kontenerowanej aplikacji i wdroż je na klastrze. Można również skonfigurować Horizontal Pod Autoscaler, aby automatycznie skalować liczbę replik w zależności od obciążenia. AKS pozwoli zarządzać kontenerami na większą skalę i jest dobrym krokiem rozwojowym, jednak należy uważać na zużycie zasobów (limit budżetu). Monitorowanie i logi. Dodaj system monitorowania i centralnego logowania. Na platformie Azure wykorzystaj Azure Monitor i Application Insights, które zbierają metryki i logi aplikacji. Azure Monitor gromadzi dane obserwowalności takie jak logi i metryki, natomiast Application Insights zbiera szczegółowe telemetrie aplikacji (traces, wyjątki itp.). W aplikacji zaimplementuj logowanie (np. wbudowany logger ASP.NET lub Serilog) tak, by trafiało ono do App Insights. Dzięki temu uzyskasz pełną widoczność działania systemu: jak podkreśla literatura, „monitoring i logowanie to cisi bohaterowie DevOps – zapewniają widoczność w czasie rzeczywistym, wczesne wykrywanie błędów, optymalizację wydajności, bezpieczeństwo i cenne dane do rozwiązywania problemów”. W Azure portalu ustaw alerty (np. na wzrost liczby błędów) i dashboardy do śledzenia stanu aplikacji. Automatyczne wersjonowanie. Zaimplementuj automatyczne nadawanie wersji aplikacji. Można użyć narzędzia takiego jak GitVersion lub akcję GitHub Actions, aby na podstawie konwencji w commitach generować numer wersji (semantycznie „semver”). Upewnij się, że każda publikowana wersja ma unikalny numer (np. w AssemblyInfo lub jako tag git). Automatyczne wersjonowanie ułatwi śledzenie zmian i deploymentów (np. tagi release) w przyszłości. Infrastructure as Code (IaC). Całą infrastrukturę wdrożeniową zdefiniuj w kodzie. Użyj Azure Bicep (lub ARM/Terraform) do opisania zasobów: grupy zasobów, App Service, Key Vault itp. Przykładowy plik Bicep może tworzyć potrzebne zasoby w Azure. Dodaj kroki do pipeline’a, które wykonują deployment IaC (np. komenda az deployment group create). Dzięki temu cały proces budowania środowiska stanie się powtarzalny i automatyzowalny. Jak zauważa dokumentacja, DevOps korzysta z IaC właśnie po to, aby „szybko wdrażać kod w sposób zaufany i powtarzalny”. Sekrety i bezpieczeństwo. Zadbaj o bezpieczne przechowywanie danych wrażliwych. Wykorzystaj Azure Key Vault do przechowywania sekretów (np. connection stringów do bazy, kluczy API). Skonfiguruj Managed Identity lub Service Principal, by pipeline mógł odczytywać sekrety podczas wdrożenia. W GitHub Actions użyj zaszyfrowanych GitHub Secrets do przechowywania poufnych ustawień (np. hasła). Przechowywanie sekretów poza kodem jest kluczowe – Azure Key Vault „pozwala bezpiecznie przechowywać i zarządzać wrażliwymi informacjami, takimi jak klucze API, dane uwierzytelniające lub certyfikaty”. Upewnij się, że nikt nie zamieszcza haseł bezpośrednio w repozytorium. Skalowanie aplikacji. Zaprojektuj skalowanie na wypadek większego ruchu. Dla Azure App Service wybierz odpowiedni plan i włącz autoskalowanie (np. różne instancje w zależności od obciążenia). Dla AKS włącz Horizontal Pod Autoscaler, który będzie dodawać instancje podów przy wzroście użycia CPU. Dzięki temu aplikacja automatycznie dostosuje się do liczby użytkowników. Skalowanie zapewni, że nawet przy zwiększonym ruchu aplikacja zachowa wydajność i dostępność. Quality Gate w CI/CD. Dodaj do pipeline’a analizę jakości kodu, np. z użyciem SonarCloud lub podobnego narzędzia. Skonfiguruj w pipeline fazę „Quality Gate”, która sprawdzi, czy kod spełnia zadane metryki (brak krytycznych błędów, odpowiedni poziom pokrycia testami itp.). W Azure Pipelines można dodać task Publish quality gate result, który wyświetla status jakości w podsumowaniu builda. Jeśli Quality Gate nie zostanie osiągnięty, pipeline powinien zakończyć się niepowodzeniem, blokując wdrożenie. W ten sposób wymusisz dodatkową kontrolę jakości (np. zero błędów krytycznych przed deploym). Self-hosted agent. (Opcjonalnie, najtrudniejsze) Rozważ użycie własnego agenta CI zamiast hostowanego. Można uruchomić maszynę wirtualną w Azure i zainstalować na niej agenta Azure DevOps. Self-hosted agent daje pełną kontrolę nad środowiskiem budowania – przydaje się, gdy potrzebujesz zainstalować niestandardowe narzędzia lub zachować sekrety w izolowanym środowisku. Wielu decyduje się na takie rozwiązanie, gdy kwestie bezpieczeństwa lub zgodności są krytyczne. Należy jednak pamiętać, że wymaga to utrzymania własnej infrastruktury CI. Jeśli budżet jest ograniczony (np. $10 na subskrypcję edukacyjną), można na początek pozostać przy agentach hostowanych. Prezentacja projektu. Przygotuj krótkie demo aplikacji i omów użyte technologie. Pokaż działanie endpointów (/, /products), a także działanie pipeline’ów (CI i CD), np. w formie pokazowego rollout’u do Azure. Wyjaśnij decyzje projektowe: dlaczego wybrano .NET, Docker, AKS, Key Vault, itp. Odpowiedz na pytania dotyczące konfiguracji (np. jak działa skalowanie, jak zarządzasz sekretami, jakie są etapy pipeline’u). Demonstracja powinna być płynna i pokazywać, że aplikacja działa stabilnie oraz spełnia wszystkie wymagania projektu.
